## Phase 1b — Browser verification (Firefox ARM64)

### Test A — endpoint contract: 14/14 pass

`harvest` starts a shift and returns `workEndTime`; a second call mid-shift
returns `not_ready`; after the shift it credits `pendingWool` into `wool`;
`claim_task` credits 5,000 and then reports `already_claimed`; unknown task →
`not_found`; `invite` returns an `id`; withdraw rejects `invalid_wallet`,
`min_withdraw_error` and `insufficient_wool`, then succeeds, debits, stamps
`lastWithdrawTime` and appends to `withdrawHistory`.

All responses carry the `{success, errorCode?}` shape the bundle's
`if(!e.ok||!t.success)` branches consume, and the missing-`x-init-data` case
returns **401**, which is what triggers the client's frozen auth modal.

### Test B — client clock maths: 6/6 pass, and one real discovery

Re-deriving `U()`, `G()` and `K()` from the decompiled source exposed a quirk:

**`U()` adds `252e5` ms — that is 252,000,000 ms = 70 hours, not 7.**
A genuine UTC+7 shift would be `252e7`. So `u = new Date(t + 252e5)` shifts the
wall clock **+2 days 22 hours**, not +7 hours.

Because 70 h ≡ 22 h (mod 24 h), combined with the local offset the "15:00"
withdraw cutoff still lands on a **fixed daily instant**: measured at
**10:00 UTC** every day on this UTC+7 host. So the once-per-day lock behaves
consistently — but it is *not* the 15:00 or the 08:00 the UI text implies.
`K()` (the payout flag) does use `setUTCHours(8,0,0,0)` and is a true 08:00 UTC.

Two consequences worth knowing:

1. The comment "Shift duration: 3 mins" and the actual `workEndTime` are
   unrelated — the server decides, and the mock confirms the client just
   renders whatever it is handed.
2. Anyone reimplementing the withdraw lock should compute the cutoff on the
   server, not copy `U()`. Copying it reproduces the 70-hour bug.

### Cross-check against the code

Every string visible in the screenshots resolves to an i18n key that exists in
**32/32** locale chunks (`yield_per_shift`, `status_ready`, `withdraw_wallet`,
`withdraw_btn`, `withdraw_empty`, `ref_reward_val`, `tab_farm`,
`tab_withdraw`). The static `index.html` does **not** contain them — they are
injected at runtime by `X()` from `data-key` attributes. That is why grepping
the HTML for the visible text returns 0 and is expected, not a defect.
